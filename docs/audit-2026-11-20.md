## 3. End-to-end check — Almere, z14

Run with headless Chromium (Playwright) against `npm run dev`, with the
location seeded to 52.3508, 5.2647 at z14 and the default layers.

**Confirmed**
- Basemap tiles load and render (OpenFreeMap; no MapTiler key was available
  to the sandbox, and the code path differs only by URL).
- The Overpass request leaves the browser exactly as specified: one batched
  POST covering 4 tiles; headers `content-type:
  application/x-www-form-urlencoded`, `accept: application/json,
  */*;q=0.8`, nothing else app-set; body `[out:json][timeout:40];` with a
  union of the shade, off-leash and water selectors.
- Retry and rotation work: 3 attempts on kumi.systems (504 from the gateway,
  then two client timeouts), rotation to overpass-api.de, a readable final
  error after ~130 s; the UI went non-blocking at 50 s as designed.

**Not confirmed: features on the map.** From this cloud, no Overpass
instance answers even with its host allow-listed. overpass-api.de resets the
TLS handshake, and kumi.systems and private.coffee accept the connection and
never reply. The basemap host on the same proxy works, so upstream is refusing
datacenter egress. That's the same pattern the Phase 2 note blamed on "the
sandbox", and it is **a data point for §4**: public Overpass does not reliably
serve server or cloud IPs.

I didn't substitute a recorded response, because that would test the parser,
not the claim. To close this out, run the steps under "Phase 2 — verification
status" in CLAUDE.md §12 from your own browser (about 2 minutes).

One behavioural finding from the run: when the primary instance hangs
silently, the user sees nothing for ~2 minutes (3 × 45 s on kumi) before
`.de` is tried. A timeout with **zero bytes received** is a different signal
from a 504 or a 429; rotating after the first of those would cut that to
~45 s. This hasn't been changed, because it's a policy decision.

## 4. Stack audit — what I'd keep, and what I'd replace

Your goal has shifted since CLAUDE.md was written: **run on your own server,
usable by anyone, without overloading it.** The spec currently forbids the
server being in the request path (§2.4) and is built around avoiding one.
Here is my honest read.

### The core problem: public Overpass as the runtime backend

About half the code (retry loop, circuit breaker, `/api/status` parsing,
session budget, the 406 saga, the CORS pinning, batching, the latency budget,
the proxy seam and the recon tooling) exists to make a volunteer-run query
engine behave like a tile server. It still costs every user 1–45 s and several
MB per new area. It fails in ways you can't diagnose: two whole sessions went
into misreading those failures. Its operators can't tell your users apart,
and §9 already admits it won't scale. It's also the opposite of what you now
want. Proxying it through your server concentrates every user onto one IP,
which the Overpass policy disfavours, and today's run suggests datacenter IPs
are treated worse still.

**Everything this app shows from OSM is static data that changes over weeks:**
benches, bins, forests, `dog=*` and surfaces. Querying it live is the wrong
tool.

### Recommendation: build your own vector tiles; serve them as static files

```
weekly cron on your server (or any build box)
  planet.osm.pbf ──osmium tags-filter──▶ ~1–2 GB of only our tags
                 ──Planetiler / tilemaker (custom profile)──▶ pawpath.pmtiles
                                                              (one file, a few GB)
Browser
  MapLibre ──HTTP range / z/x/y──▶ your server (Caddy/nginx or `pmtiles serve`)
                                    └─ Cloudflare free proxy in front: edge cache
```

- **Server load is essentially zero.** It's static file serving, and with
  Cloudflare's free proxy in front most requests never reach the VPS. Anyone,
  anywhere, at any traffic level, costs about the same.
- **Equal quality worldwide** (§2.3) holds better than today, because it's
  built from the full planet. NL and DE could be built first from Geofabrik
  extracts if disk is tight.
- **Instant.** A tile is ~10–100 KB, there are no retries or warm-up queries,
  and it works offline from the browser cache.
- **The dog-specific logic survives intact.** `layers.ts` selectors and level
  derivations (`offLeashLevel` with its `dog=yes` rule, `wasteLevel`, surface
  → paw risk) move into the tile-build profile. That's the same table, run at
  build time. The tests stay.
- **Phase 5 gets easier.** Polygons arrive pre-assembled (multipolygon
  relations included, which is currently an open seam). Paw-heat recolouring
  becomes a MapLibre style expression on a `paw_risk` property.
- **Phase 8 gets easier.** Municipal `losloopgebieden` GeoJSON is merged into
  the same build, with no runtime fetching at all.
- **Cost:** a weekly build. A planet `osmium tags-filter` pass needs ~100 GB
  of free disk and modest RAM; Planetiler on the filtered file is quick. If the
  VPS is small, start with Europe, or rent an hourly box for the build. Data is
  up to a week old, which is irrelevant for benches.

**What gets deleted:** `overpassClient`, `overpassHealth`, `overpassRetry`,
`overpassQuery`, `overpassTileSource`, `cachedTileSource`, `proxyTileSource`,
`tiles.ts` (the grid), `useTileFeatures`, the DevPanel connectivity tester,
the recon page and their tests: about 5,600 of the repo's 8,200 lines. The recon page becomes a script
that prints per-layer feature counts from the built tiles, which is a better
coverage answer anyway because it covers every city at once.

**What stays:** Vite, React, TS, Tailwind, MapLibre, `layers.ts` semantics,
`surface.ts`, the paw-model config, `storage.ts`, geolocation, MapView (it
gains a vector source), the disclaimer, attribution, the ad slot, and every
rule in §6.

Overpass can remain a dev-only tool for checking a tag before adding it to
the profile.

### Basemap: OpenFreeMap now, self-host later

Switch the default from MapTiler to **OpenFreeMap**: no key, no quota,
public and commercial use allowed. It's already verified working in this
session through the existing `VITE_MAP_STYLE_URL`. This removes launch
checklist item 3 and a key that is visible in every client anyway. If you
later want zero third parties, serve a Protomaps or OpenMapTiles basemap
`.pmtiles` from the same server. MapTiler stays one env var away.

### Weather (Phase 3): Open-Meteo, with one catch

Keep Open-Meteo direct from the browser. It's global, keyless, and has the
shortwave radiation the paw model needs, which most alternatives lack. The
catch: **its free tier is non-commercial.** The day the ad slot goes live,
you need their paid plan or a self-hosted Open-Meteo (open source, runs on
your server). A small caching endpoint on your server, rounding coordinates
to ~0.1° and caching for an hour, would collapse thousands of users onto a
few hundred upstream calls. That's worth adding if traffic appears, not
before.

### Water warnings (Phase 6): skip the Worker + D1

n8n already runs on your server. Have it write one static
`water-warnings.json` next to the tiles every few hours. That's one cached
file per client, with no database and no Worker.

### Place search: comply now, upgrade later

Nominatim forbids search-as-you-type. Change it to submit-on-Enter now, which
is a 20-line change, or move to **Photon** (built for autocomplete). Photon is
available as a public instance at photon.komoot.io, or self-hosted later.

  geolocation denied, someone in Melbourne lands in Flevoland. A world view
  plus a search prompt is fairer (§2.3).
- `APP_CONTACT_URL`: `https://github.com/unrlnt/dogwalkmap` is a candidate
  *if* the repo is or will be public. A dead link is worse than "unset".
- Geometry is downloaded for polygon layers today but only their centre
  point is drawn.
